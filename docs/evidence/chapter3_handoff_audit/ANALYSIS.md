# 基线、重复性与初始化审计

## 缺失基线与重复性核查

在同一240条TEST上，用1199发布片段中的TRAIN根计算路线类型成功率，得到路线查表Brier **0.11141**，全局TRAIN常数 **0.12160**，冻结事件模型 **0.09570**。因此路线信息确实解释部分改善，但不能用不同采集批次的Brier直接计算方法增益。该比较只有4根、已检查TEST，不能据此证明状态或接口预测带来的因果价值。

距离规则6/12与8/12的差别来自两个条件：root1/x5、root2/x3由失败变为成功。12对的候选、量化延迟（20ms）、查询及发布时记录的13维root状态全部一致；所以不能再用“查询状态不匹配”解释这两次差异。尚未验证完整接触求解器/隐藏状态与后续执行一致，差异来源未定位。后续必须固定重复协议、记录执行与初始化状态，不能选择较好的那次当方法优势。逐对记录见`baseline_audit.json`。

## 交回初始化代码审计

`ditch_ground_handoff.py`在首次远岸接触后的策略边界调用`IsaacPathRollout.resume_ground_lanes`，物理状态不重置。该函数调用controller/lower reset；ESO、扰动估计、侧倾角速度滤波器归零；H75偏移/滤波及历史帧reset，历史mask清零后记录当前一帧。前次参考和命令按落地实测速度/转向等赋值，路径进度就近投影。没有以真实历史独立运行的预热阶段。可确定的是“估计器和策略历史冷启动”，不能由此确定“冷启动造成失败”。腾空期直接沿用地面ESO也未必正确，应与接触模式一致的预热/状态初始化作对照。

现有NPZ包含root、观测和控制器历史，但不是完整可还原的Isaac快照（缺完整关节/执行器/延迟状态和接触求解器状态）。短分叉应优先同起点重跑前缀、在实际交接截面分叉；若做状态移植，先与重跑前缀基线区分，不能仅恢复root就称同状态重放。标签后缀虽为1–2秒，运行预算仍要包含前缀。
